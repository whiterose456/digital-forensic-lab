# CASE #0147 — The Vanishing Server

**An interactive digital forensics investigation simulator built with React and TypeScript.**

A payroll server has triggered an alert for unusual outbound activity. Explore the available logs, investigate suspicious artifacts, correlate events, and reconstruct the fictional incident timeline.

This project puts you in the role of a junior forensic investigator: the evidence includes both routine system activity and suspicious clues, so the challenge is to separate background noise from a plausible compromise chain.

> **Project scope:** Educational simulation using predefined fictional case data. It is not a live forensic acquisition or incident-response tool.

## Case briefing

At **09:33 UTC**, a network perimeter monitor reports high-volume outbound activity associated with an internal server hosting sensitive payroll records. No authorized data export was scheduled.

Your mission is to examine the available evidence and determine how the incident unfolded.

### Investigation objectives

- Examine authentication, network, file, and system activity.
- Filter evidence by keyword and category to find relevant artifacts.
- Inspect raw log details and record notes for individual evidence items.
- Pin suspicious artifacts to a timeline and arrange them chronologically.
- Form a hypothesis and compare your findings with the case's expected compromise chain.

## Features

- **Evidence explorer** — Browse the case's predefined forensic records.
- **Search and filtering** — Narrow evidence by keyword and event category.
- **Artifact inspection** — Review record details and raw log payloads.
- **Rule-based anomaly scoring** — Highlight suspicious patterns such as repeated failed logins, sensitive file access, archive creation, and unusual outbound connections.
- **Investigation timeline** — Pin and sort evidence to reconstruct the sequence of events.
- **Analyst notes and hypothesis** — Record observations and develop an explanation.
- **Investigation summary** — Track progress against the case's expected findings.
- **Browser persistence** — Keep pinned evidence, notes, and hypothesis text in `localStorage`.

> Anomaly scores are generated by application-defined rules and heuristics, not a trained machine-learning model. They are investigative hints, not proof that an event is malicious.

## Investigation workflow

1. **Read the briefing.** Identify the affected host, time window, and reported incident.
2. **Explore the evidence.** Search the records and separate routine activity from potentially relevant events.
3. **Inspect suspicious artifacts.** Read the raw payload and capture why each item matters.
4. **Correlate events.** Pin evidence to the timeline and sort it by timestamp.
5. **Form a hypothesis.** Explain the likely access method, targeted data, and outbound activity.
6. **Validate the reconstruction.** Compare your selected evidence with the case's expected compromise chain.

├── data/

├── lib/
│   └── anomaly-detection.ts # Rule-based anomaly scoring and correlation
├── types/
│   ├── analysis.ts          # Anomaly-analysis types
│   ├── case.ts              # Case metadata model
│   └── evidence.ts          # Evidence model

The application separates the case dataset, typed models, anomaly-analysis logic, and UI components. The current scenario and evidence are defined in code rather than collected from a live system.

## Learning outcomes

This project is intended to help learners practice:

- Reading and interpreting log artifacts.
- Distinguishing routine activity from suspicious indicators.
- Correlating authentication, file, and network events.
- Reconstructing a timeline from multiple evidence sources.
- Writing down investigative reasoning and testing a hypothesis.
- Building a typed, component-based security-education interface.

## Limitations

- The case uses predefined, fictional evidence.
- The application does not acquire disk images, collect live endpoint telemetry, or investigate real hosts.
- Anomaly detection is rule-based and may produce false positives or miss suspicious activity.
- Notes, pinned evidence, and hypothesis text are stored in the current browser's `localStorage`; they are not synchronized to a server.
- The case's expected findings are built into the simulator for educational validation.

## Possible future improvements

- Add more independent case scenarios and evidence datasets.
- Add screenshots and a guided walkthrough of a completed investigation.
- Export investigation notes, selected artifacts, and timelines as a report.
- Add evidence provenance and integrity checks for imported datasets.
- Support carefully validated, sanitized external forensic datasets.

## Ethical use

Use the simulator for education and authorized security training. Any real-world forensic work should follow applicable authorization, privacy, evidence-preservation, and chain-of-custody requirements.
